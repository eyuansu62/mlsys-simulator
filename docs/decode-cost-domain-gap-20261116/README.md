# 11-16 runtime-cost 校准对 11-11 eager 9070XT 场景可解释多少失准（Step 1）

CPU 侧量化分析，复用仓库自身成本机制，不新增任何拟合。全部结论 `hardware_validated=false`。
复现脚本：[scripts/analyze_decode_domain_gap.py](../../scripts/analyze_decode_domain_gap.py)。

**前提**：11-11 研究为 eager MRv1、input 256、output 16，decode 上下文约 257–271；11-16 校准域
绑定 `graph_full_and_piecewise_configured` / `RocmAttentionImpl`，保留 decode 形状
**context 1024–1043、B 1–16**。两者在**执行模式**与**上下文**两个维度都不同域。

## 与 PR #9（runtime-cost 校准 v1.21）的关系：同症状、不同问题

PR #9（`runtime-cost-calibration-v121`，已合并）给 **Graph/MRv2/async/RocmAttentionImpl、ctx≈1024–1043**
域加了 opt-in、不可变、按 Runtime 域绑定的解析成本，域内 MAPE 37.82%→9.72%，并**自己声明**
"不覆盖 eager、不认证 online SLA、非新的盲采集"。本研究与其是**同一条诚信叙事的连续两步**，
不是同一问题的两次观察：

- **同症状**：都由"decode 在该卡上被低估"触发；都坚持"不外推、不过度主张"。
- **域是硬边界，不是软边界**：本场景（11-11 SLA）= **eager MRv1、C≈256**，恰是 #9 声明不覆盖的区域；
  用 #9 机制查 ctx=257 会**强制**抛 `CALIBRATION_MISMATCH`（§1）。#9 的 9.72% 对本场景**不构成任何精度主张**。
- **根因不同**：#9 补的是 Graph 域**漏掉的固定 Runtime 工作与 attention**（模型完备性缺口，域内加拟合分量即可）；
  本场景在 C≈256 是**批处理不变的权重搬运主导（~88%）、名义斜率结构性偏平 + β 高估 decode 带宽效率**——
  成本表达式的**形式**对短上下文就是错的（§3：连非法外推也只收窄 C1 绝对缺口 −32.4%→−9.9%，闭不了斜率
  实测 +38.9% vs 外推 +3.2%）。
- **认识论地位不同**：#9 = 已合并的域内校准（retrospective，自认非盲采集）；本研究 = **冻结的前向盲留出**，
  本身不下结论，只为让未来 eager 域修正在**未见点**上被诚实检验。
- **不是重复免责声明**：#9 把"不覆盖 eager / 不认证 SLA"写成 scope 一行；本研究把它**量出来**（绝对 vs 斜率
  两个独立缺陷）+ **诊断出结构根因**（§4/§5）+ **冻结独立留出**（Step 2），并禁用了已消耗的 11-11 点。

一句话：#9 关死了 **Graph/长上下文域**；本研究顺着它自己划的线，把 **eager/短上下文域**开成一个
**独立、可验证、待 GPU 盲测**的问题。

## 1. 域边界被正确强制执行（工具不会误用校准）

对 11-16 拟合模型查询 11-11 形状（decode, ctx=257）：

```
SCOPE ENFORCED: Analytical cost query is outside the retained shape/context domain
```

即 `corrected_analytical_step` 抛出 `CALIBRATION_MISMATCH`，拒绝在保留形状/上下文域外应用拟合。
因此 11-16 校准**不构成对 eager C≈256 场景的任何精度主张**；下文所有“外推”仅为分析，不是预测。

## 2. 精确复现 11-11 默认预测

课程 η=0.6243、β=0.9054、launch 2µs / framework 5µs、无 analytical cost 时，decode 中位步长：

| B | 复现 ms | 11-11 研究值 |
| ---: | ---: | ---: |
| 1 | 14.326 | 14.326 |
| 2 | 14.401 | 14.400 |
| 4 | 14.550 | 14.549 |
| 8 | 14.848 | 14.846 |

与分析脚本一致，证明本分析所用的模型/参数与 11-11 预测完全同源。

## 3. 域外外推（仅分析）：能解释绝对量级，解释不了批处理斜率

把拟合的 4B decode spec（`nonattention ×1.1188`、`attention ×1.3326`、
`attention_fixed 6.952µs×36 层`、`runtime_fixed 4706.3µs`）非法地外推到 C≈265，与 11-11 实测对比
（实测为 3 次 fresh Runtime 的 TPOT 中位）：

| B | 实测 ms | 默认预测 ms | 默认误差 | 外推校准 ms | 外推误差 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 21.204 | 14.326 | −32.4% | 19.109 | **−9.9%** |
| 2 | 22.584 | 14.401 | −36.2% | 19.197 | −15.0% |
| 4 | 22.684 | 14.550 | −35.9% | 19.375 | −14.6% |
| 8 | 29.461 | 14.848 | −49.6% | 19.730 | −33.0% |

**C1→C8 斜率**：实测 **+38.9%**，默认预测 **+3.6%**，外推校准 **+3.2%**。

结论：
- 11-16 拟合里的经验每步截距（`runtime_fixed` ≈ 4.7 ms，graph 域）若能外推，能把 C1 的绝对缺口
  从 −32.4% 收窄到 **−9.9%**（约闭合 70% 的绝对偏差）。
- 但它**完全闭合不了批处理斜率**：外推后仍是 +3.2%，远低于实测 +38.9%。绝对量级与斜率是两个独立缺陷。

## 4. 分量分解：短上下文下步长被“权重搬运”主导，模型斜率天然偏平

在代表上下文 C=265、11-11 默认规格下的名义分量（ms）：

| B | 总计 | linear | embedding+output | misc | framework | attention |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 14.327 | 12.614 | 1.345 | 0.222 | 0.005 | 0.141 |
| 4 | 14.551 | 12.619 | 1.347 | 0.233 | 0.005 | 0.347 |
| 8 | 14.850 | 12.626 | 1.349 | 0.249 | 0.005 | 0.622 |

- `linear`（权重搬运 GEMM）约 **12.6 ms，占步长 ~88%，且随批处理几乎不变**（权重每步只读一次）。
- `attention`（KV 读取）很小，B=1→8 仅 0.141→0.622 ms（4.4×），在 14.8 ms 总步长里只贡献 +2.1 ms 增量的一部分。
- 因此在 C≈256 下，**名义宏的批处理斜率结构上就是偏平的**：无论 attention 斜率如何，都被批处理不变的
  权重搬运项稀释。这是模型无法表示实测 +38.9% 斜率的结构性原因，不是参数没调好。

## 5. 归因：β 高估了 decode GEMM 的带宽效率

Qwen3-4B BF16 权重约 8.04 GB（≈4.02B 参数 × 2B，含 tied embedding）。

- 模型 C1：内存受限分量合计 ≈ 14.18 ms → 有效带宽 ≈ 8.04 GB / 14.18 ms ≈ **567 GB/s ≈ 峰值 640 GB/s 的 89%**。
- 实测 C1 = 21.20 ms：若不扣固定开销 → ≈ 379 GB/s ≈ **59% 峰值**；若扣 graph 域 `runtime_fixed`≈4.7 ms →
  ≈ 487 GB/s ≈ **76% 峰值**。

即实测 decode 的有效带宽效率约 **59–76% 峰值**，而模型假设接近 89%。课程 β=0.9054 来自
LN/Softmax primitive 的迁移，**系统性高估了 eager 下逐 token decode GEMM 的实际带宽效率**——这是
TPOT 约 2× 失准（0/39 达精度目标）的主因，与 11-11 README 的“主要可见偏差在持续 decode 成本”一致。

## 6. 对下一步（Step 2）的含义

现有数据在域内**无法识别** eager 短上下文场景的两件事：

1. **eager 每步固定截距**：11-16 的 `runtime_fixed`≈4.7 ms 是 graph 域、C=1024 的值，不能合法搬到 eager C≈256。
2. **短上下文批处理斜率**：名义宏在 C≈256 被权重搬运主导、斜率偏平，需要真实低并发、短上下文的
   eager 观测才能钉住 KV/发射/混批随批处理增长的斜率。

因此 Step 2 需在 9070XT 上冻结并执行一个**低并发 + 长输入**的**新**留出：新预注册并发网格
（不复用已消耗的 8/16/32）、测前 SHA 承诺、3 次 fresh 重复、不回拟合。该实验同时检验
TPOT 精度与 C1→C8 批处理斜率是否在修正后的模型下收敛。
